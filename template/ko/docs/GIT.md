# Git 운영

사람 승인자와 여러 AI 에이전트가 이 저장소를 함께 쓰는 방식이다. 채택 결정은 [ADR-0001](adr/0001-adopt-gitops.md)에 있다. 보호 브랜치·커밋 칸·비밀 패턴 값은 `gitops.config.json`이 기준이다.

## 목적과 범위

Git을 쓰는 목적은 **에이전트가 바뀌거나 세션이 끊겨도 작업의 의도·결정·현재 상태를 복원할 수 있고, 승인자가 그 작업을 안심하고 받아들이거나 되돌릴 수 있게 하는 것**이다. 필요한 것은 세 가지다.

1. 기록: 무엇을 왜 바꿨는지와 지금 어디까지 했는지가 남아, 다음 담당자가 의도·결정·현재 상태를 복원한다(커밋 양식, 작업별 인계, ADR).
2. 판정 지점: 승인자가 받아들일지 정하는 곳이 하나 있다(PR, 판정용 본문, 독립 검수 1회).
3. 되돌림: 잘못되면 되돌릴 수 있다(보호 브랜치 직접 수정 금지, revert).

- 막는 대상은 협조하는 에이전트의 **실수**다. 모든 변경을 되돌릴 수 있다는 전제다. 일부러 꼬아서 장치를 우회하는 경우는 범위 밖이다.
- 멈춤 기준: 검수에서 나온 문제 중 실수로 생길 수 있는 것만 고친다. 의도적 우회는 범위 밖으로 기록만 한다. 위 세 가지에 들어가지 않는 장치는 더하지 않는다.
- 사람의 새 결정·반복 질문·검토 시간·병합 확인을 따로 센다. 승인된 통상 선택은 진행하고, 새 범위·권한·저장 데이터·외부 효과·유효 결정의 변경만 질문한다. 승인 대기 중에는 독립 작업을 진행하며, 대기 시간이 승인을 대신하지 않는다.

## 역할

- 에이전트: 작업, 커밋, PR 작성. 판정용 PR 본문을 쓴다.
- 조정 담당 에이전트: 승인된 범위를 배정하고 공유 진행 목록을 단독 갱신한다. 요구·권한을 새로 승인하지 않는다. 총괄 에이전트가 맡으며 사람이 목록을 관리할 필요는 없다.
- 독립 검수 에이전트: 작성자와 다른 새 맥락에서 요청에 없던 변경을 나열한다. 읽기 전용이며 검수 입력과 절차는 아래 'PR' 절을 따른다.
- 승인자(사람): PR을 **판정하고 병합한다**. diff를 줄 단위로 읽는 대신 판정용 본문과 독립 검수 결과를 본다. 어디까지 읽을지는 아래 위험 등급이 정한다. 에이전트는 병합하지 않는다. 승인자가 여러 명이면 경로별 담당을 CODEOWNERS에 적는다.

## 위험 등급

모든 PR은 승인자가 병합한다. 등급은 승인자가 **어디까지 읽을지**를 정하는 기준이다. 등급은 PR에서 바뀐 파일 경로로 정하고, 여러 등급이 섞이면 가장 높은 등급을 따른다. 목록에 없는 경로는 중위험이다. PR 본문의 '위험 등급' 칸에 작성 에이전트가 적는다.

| 중위험 | `README.md`, `.gitmessage`, 목록에 없는 경로 | 문서는 바뀐 문단, 코드는 바뀐 함수와 그 테스트 |
| 저위험 | 프로젝트 경로: 생성 산출물, 오탈자·서식만 바꾸는 문서 등 | 본문의 "요청 대비 결과"와 "요청에 없는데 에이전트가 정한 것" |

- 고위험에 규칙·도구·요구 기준 파일을 넣은 이유: 에이전트가 고친 규칙이나 판정 기준이 승인자 모르게 바뀌지 않게 하려는 것이다.
- PR과 별개로, 다음 행동은 실행 전에 매번 승인자의 승인을 받는다: 저장소 공개 범위 변경, 외부 시스템의 데이터를 일부러 만들거나 지우는 일, 외부 댓글·메시지 전송, 자격증명 취급. 허용된 조회의 부수 쓰기(조회 로그 등)는 기록만 한다. 외부 시스템별 규칙은 AGENTS.md '프로젝트 규칙'에 둔다.

## 브랜치

- 이름은 `<커밋 type>/<짧은 설명>`으로 한다(예: `fix/login-timeout`, `docs/git-rules`).
- 새 작업 브랜치는 원격을 읽은 뒤 `origin/<보호 브랜치>`에서 만든다. 로컬 보호 브랜치는 낡아 있을 수 있으므로 기준으로 쓰지 않는다.
- 병렬 작업은 worktree를 나눈다. 보호 브랜치(`gitops.config.json`의 `protectedBranches`)에는 직접 push하지 않는다.

## PR

- 작업은 하나로 받아들이거나 되돌릴 수 있는 완료 목표다. 같은 목적·승인 범위·복구 단위의 하위 작업은 담당자 한 명이 한 브랜치·PR로 정리한다. 다른 요구·위험을 억지로 묶지 않고 고위험 크기 기준을 지킨다.
- 본문은 [PR 양식](../.github/pull_request_template.md)의 판정용 형식으로 쓴다. 가장 중요한 칸은 "요청에 없는데 에이전트가 정한 것"이다.
- 판정 기준은 사람이 정한 요청이다(Issue, 작업 요청, ADR에 승인자 결정으로 기록된 것). Issue는 필수가 아니며, 요청의 위치를 본문에 적는다.
- 진행 상황은 인계 기록이나 새 댓글 초안에 남긴다. 최종 범위·근거·검증 SHA가 바뀌면 PR 본문의 해당 칸만 갱신하고 이전 검수 SHA는 검수 기록에 보존한다. 댓글 전송은 승인자가 명시적으로 요청한 경우에만 한다.
- 독립 검수자는 요청·기준 문서·diff·근거를 먼저 읽고 본문과 대조한다. 검수한 base/head SHA, 지적 위치, 미확인을 남긴다. 변경 후에는 영향받는 부분을 다시 확인한다. 전체 검수 1회와 필요한 지적 수정 확인을 기본으로 하되 실제 결함·새 요청은 추가 검증한다.
- 조정 담당자는 준비된 PR과 관련 질문을 묶어 제시한다. 통상 선택과 새 결정 필요를 구분하고 새 질문에는 추천안·대안 비용·영향 작업을 적는다. 일괄 제시는 에이전트 병합 권한을 만들지 않는다.
- 이미 낸 PR의 브랜치에 커밋을 더 push하기 전에 `gh pr view <번호> --json state`로 상태를 확인한다. 병합·종료됐으면 그 브랜치에 push하지 않고 `origin/<보호 브랜치>`에서 새 브랜치를 만든다. 병합 직후 같은 브랜치에 push한 커밋은 보호 브랜치에 들어가지 않는다.
- 병합 방식은 하나만 쓰고 저장소 설정에서 나머지를 끈다.

  - merge commit: 작업 브랜치의 커밋이 그대로 들어가므로 commit-msg 훅이 검사한 메시지가 보호 브랜치에 남는다.
  - squash: PR 하나가 커밋 하나가 된다. squash 메시지는 GitHub 화면에서 쓰므로 훅이 검사하지 않는다. 병합자가 PR 본문에서 배경·결정과 버린 대안·검증·위험을 옮겨 쓰고 다음 할 일은 뺀다.
- 결함은 revert PR로 복구하고 보호 브랜치의 이력을 다시 쓰지 않는다.

## 시작과 공유 진행 목록

1. branch·HEAD·미커밋 상태와 규칙의 기준 SHA를 확인한다. 가능한 경우 원격을 읽어 보호 브랜치·관련 PR의 최신 상태를 확인하고, 불가능하면 마지막 확인 시각을 남긴다. 사용자·상위 지시가 우선이며 미병합 제안이 권한을 확대하지 않는다. 유효한 결정은 보호 브랜치의 ADR 중 상태가 `accepted`인 것이다. 작업 브랜치·PR 안의 ADR은 상태와 관계없이 제안이다.
2. 아래 공유 목록과 관련 PR의 범위·base/head·의존 작업을 읽는다. PR 제목은 후보를 찾는 데만 쓴다. 담당자를 확인할 수 없는 겹치는 범위는 쓰지 않고 독립 작업을 진행한다.
3. 담당자·작업 범위를 등록한 뒤 작업별 인계의 작업 정의와 현재 상태 블록을 먼저 읽는다. 과거 기록은 블록이 가리키는 링크로 필요한 것만 읽는다.
4. 목록의 상태를 인계 블록·PR 실제 상태와 대조한다. 다르면 PR, 인계, 목록 순으로 믿고 목록을 고친 뒤 정정 원인 `상태 불일치`로 기록한다('효과 확인과 비용 상한').

한 clone의 worktree는 `git rev-parse --path-format=absolute --git-common-dir`로 찾은 공통 디렉터리의 `coordination/active.md` 한 곳을 사용한다. 처음 만들 때 기존 파일과 작성자가 없는지 확인한다. 목록 상단에 조정 담당 세션·규칙 기준 SHA·확인 시각을 적고, 작성자는 한 명만 둔다. 일반 파일이므로 동시 쓰기를 자동으로 막지는 않는다.

```text
작업: 요청 ID와 완료 목표
담당: 세션 / 브랜치 / worktree
기준: 규칙 SHA / 시작 base SHA / 현재 head SHA
범위: 파일·절 / 공유 자원 담당자
상태: 진행·검수 준비·사람 확인 대기·의존 대기·종료 / 상태 변경 시각
의존: 작업 ID와 고정 SHA / 확정·제안 구분
재개: 인계 위치 / 다음 행동 한 개
주의: 미커밋 상태·외부 부수 효과 / 검증 결과 위치
```

착수·범위/의존 변경·인계·종료 때 갱신한다. 겹치는 개념·용어도 조정한다. 같은 외부 계정·세션·환경을 쓰는 작업은 파일 격리와 별개로 담당자 한 명이 수행한다. 규칙·의존 SHA가 바뀌면 영향받는 담당자에게만 전달해 관련 가정과 검증을 갱신한다.

공유 목록은 위치를 찾는 로컬 색인이다. 상태 단어와 위치만 두고 세부 상태는 인계에 쓴다. 새 clone·다른 기기로 전파되지 않는다. 작업별 인계는 작업 브랜치의 `docs/handoffs/<작업ID>.md`에 남긴다(프로젝트에 다른 인계 위치가 있으면 그곳을 쓴다). 복원할 기록은 작업 브랜치에 커밋하고 필요한 원격 보존은 승인된 push 절차를 따른다. 여러 기기·사람이 함께 쓰면 공유 위치(PR draft, Issue 등)를 따로 정하기 전에는 이 목록만으로 조정하지 않는다.

## 인계와 의존 작업

- 인계에는 한 일·다음 행동·막힌 것·검증 SHA와 결과·미커밋 상태·외부 효과·의존 작업과 SHA를 남긴다. 이전 담당자의 쓰기 종료를 확인한 뒤 담당자를 넘긴다. 시간 경과만으로 소유권을 넘기지 않는다.
- 인계 맨 위에는 착수 때 쓰는 작업 정의를 둔다. 첫 구현 전에 쓰고 첫 커밋에 넣는다. 그래야 첫 커밋 전에 끊겨도 같은 worktree에, 커밋 뒤에는 브랜치에 왜·어디까지가 남는다. 요청이 Issue·ADR에 이미 있으면 위치만 적고 옮겨 쓰지 않는다. 범위·완료 조건이 바뀌면 덮어쓰지 않고 `변경: 날짜 / 이유 / 승인 위치`를 덧붙인다. 범위를 넓히는 변경은 사용자 확인이 먼저다. 오탈자 같은 작은 작업은 요청 위치 한 줄로 충분하다.

```text
요청: 원문 위치(Issue·ADR·대화 날짜)와 한 줄 인용 / 요청자
목적: 왜 하는가
범위: 안 / 밖
완료: 완료 조건과 확인 방법
전제: 승인된 결정과 출처
```
- 작업 정의 아래에는 지금 유효한 것만 모은 현재 상태 블록을 둔다. 블록은 다음 행동·막힘이 바뀌면 덮어쓰고, 그 아래 이력은 추가만 한다. 병합·종료는 커밋 없이 일어나므로 블록이 아니라 PR 상태로 확인하고, 확인하지 못하면 미확인으로 적는다. 여러 작업이 한 파일을 함께 고치면 블록을 그 파일에 두지 않고 작업별 인계에 둔다(같은 줄을 덮어써 병합이 충돌한다).

```text
상태: 진행·검수 준비·사람 확인 대기·의존 대기·종료 / 기록 시각 / head SHA / 미커밋 파일(없으면 없음)
다음: 다음 행동 한 개
막힘: 막힌 것과 해제 조건, 없으면 없음
검증: 결과 위치와 검증 SHA
근거: 이력·PR·근거 파일 링크
```
- 다음 셋은 다음 단계로 넘어가기 전에 이력에 한 줄 덧붙인다: 사용자 결정·요구 변경, 검증 결과(실패와 그 이유 포함), 외부 부수 효과 직전. 커밋할 때와 세션을 끝낼 때도 갱신하지만, 사용자 중단이나 강제 종료에서는 끝낼 때의 갱신이 일어나지 않으므로 그것에 기대지 않는다.
- 재개 담당자는 블록의 head SHA를 기준으로 `git status --short`, `git log <SHA>..HEAD`, `git diff <SHA>`를 읽는다. 기록 이후의 커밋·미커밋 변경은 확인되지 않은 작업이다. 검증하거나 미확인으로 적기 전에는 근거로 쓰지 않고, 지우지 않고 보존한다. 파일 수정 시각은 체크아웃으로도 바뀌므로 보조 단서로만 쓴다. 관련 인계와 의존 변경을 읽고 다음 행동부터 재개한다. 다른 SHA의 검증 결과를 재사용하지 않는다.
- 이전 담당자가 응답하지 못하면 사용자에게 쓰기 종료를 확인받는다. 사용자도 확인할 수 없으면 간격을 두고 두 번 `git status --short`와 파일 수정 시각이 같은지 보고, 그 근거를 인수 기록에 남긴다. 그래도 확실하지 않으면 그 worktree에 쓰지 않는다. 블록의 head SHA에서 새 worktree·브랜치로 시작하고, 원래 세션이 돌아오면 diff로 합친다.
- 에이전트별 구현 작업은 한 번에 하나를 기본으로 한다. 대기 중 독립 작업으로 전환할 때는 대기 이유·해제 조건·담당자를 남긴다. 가능한 승인 범위 작업이 없으면 조건을 보고하고 임의로 범위를 늘리지 않는다.
- 선행 A가 미병합이면 후속 B는 독립적인 조사·검증 설계·초안을 진행한다. A의 미승인 결정에 의존하는 구현은 보류한다. 이미 승인된 요구의 구현만 의존하면 A의 고정 SHA를 읽거나 임시 실험 기준으로 쓸 수 있다.
- 불가피한 로컬 의존 작업은 한 단계만 준비하고 A의 ID·SHA, B 고유 변경, 통합 순서를 기록한다. A 반영 후 실제 보호 브랜치에 B 고유 변경을 맞추고 영향받는 검수·검증을 다시 한다. squash 뒤 PR 대상 변경만으로 끝났다고 보지 않는다.
- A 폐기·revert 시 B의 의존 부분을 재검토한다. 함께 되돌릴 범위·후속 수정·외부 효과를 복구 자료에 적는다. revert가 의존 관계나 외부 데이터를 자동 복원한다고 가정하지 않는다.

## 종료와 작업 공간 정리

먼저 공유 목록에 종료·대체 상태와 결과 위치를 남겨 낡은 작업을 현재 기준과 구분한다. 종료 항목은 `작업 / 결과 PR / 반영 SHA / 작업 공간 상태` 한 줄로 줄인다. 종료된 인계의 지속할 이유는 커밋·ADR에 남긴다. 미완료 기록은 보존한다.

여러 작업에 걸쳐 쓰는 기록 파일(작업 원장 등)은 단계가 끝나거나 '효과 확인과 비용 상한'의 읽기 경보값을 넘으면 지난 기록을 이력 파일로 옮긴다. 옮기는 커밋에는 이동만 넣고 `git diff --color-moved=plain`으로 내용이 바뀌지 않았는지 확인한다. 원래 절은 지우지 않고 이력 파일 링크를 남긴다.

삭제 전 실제 PR의 병합/종료 상태, 결과 반영, 사용 중인 세션, 다른 작업의 의존을 확인한다. tracked·untracked·ignored 파일과 미커밋 변경을 점검해 필요한 기록을 보존한다. squash 때문에 `branch --merged`만으로 반영을 판정하지 않는다. 상태·담당자가 미확인이면 보존한다.

삭제가 승인된 대상만 절대 경로를 확인해 정리하며 강제 삭제를 기본으로 쓰지 않는다. 기본 worktree는 제거하지 않는다. 기본 폴더의 기준 브랜치 이동과 연결 worktree 제거를 구분한다. 활동 종료 표시가 물리적 삭제 승인은 아니다.

정리 시점: 조정 담당자가 주 1회 또는 완료 목표 5개마다 병합·종료된 PR의 worktree·로컬 브랜치·원격 브랜치 목록을 만들어 승인자에게 한 번에 묻는다. 삭제·보존이 정해지면 공유 목록의 해당 종료 항목도 지운다. 정리하지 않으면 병합된 작업 공간이 계속 쌓인다.

## 효과 확인과 비용 상한

첫 적용은 적용 시작부터 5개 완료 목표 또는 2주 중 먼저 도달하는 시점에 점검한다. 완료·인계 기록에 새 결정 수·반복 질문 수·사람 검토 시간·병합 확인 수·대기 이유를 남긴다. 추정과 미측정을 구분하고 기준 자료 없이 개선율을 만들지 않는다.

인계 시험은 첫 점검 때 한 번 이상 한다. 이전 대화를 모르는 새 맥락의 에이전트에게 저장소와 인계만 주고 목표·유효 결정·완료와 미완료 범위·다음 행동·미확인 항목을 쓰게 한다. 시험을 준비한 쪽이 미리 써 둔 답과 대조해 맞은 항목 수, 추가 질문 수, 재탐색 비용(읽은 파일 수·글자 수)을 남긴다. 시나리오는 정상 교체, 첫 커밋 전 중단, 낡은 공유 목록, 의존 작업 변경이다. 답이 소스 주석이나 다른 파일에 그대로 있으면 시험이 되지 않으므로, 인계에만 있는 사실(버린 접근, 되돌린 변경 등)로 확인한다. 횟수가 적으면 파일럿이라고 적고 효과의 증거로 쓰지 않는다.

오류는 작업 로그나 후속 PR에 `정정 원인: 낡은 규칙/인계 누락/상태 불일치/동시 충돌/요구 오해/새 근거/기타; 대상 작업·PR·SHA; 재작업; 후속 수정 또는 revert; 놓친 확인 지점`을 남긴다. 후속 정정도 세되 새 근거에 따른 정당한 변경은 맥락 손실로 세지 않는다.

재개 때 읽는 분량은 글자 수로 센다(`wc -m`이나 편집기 표시). 바이트는 언어마다 글자당 크기가 달라 쓰지 않는다. 초기 경보값은 다음과 같다.

| 대상 | 경보값 |
|---|---|
| 작업 정의 | 1,500자 |
| 작업별 현재 상태 블록 | 1,000자 |
| 공유 목록 | 3,000자 |
| 재개 때 먼저 읽는 상태(공유 목록 + 자기 작업 정의·블록 + 여러 작업에 걸친 기록의 현재 단계 부분, 규칙 문서 제외) | 10,000자 |
| 재개 때 읽는 파일 하나 | 20,000자 |

파일 하나의 값은 에이전트 도구가 한 번에 읽는 양(조사 시점 약 25,000토큰)을, 표·URL이 많은 한국어 문서에서 잰 비율(약 0.8토큰/자)로 환산한 약 30,000자의 3분의 2다. 나머지 값은 한 문서형 저장소의 기존 기록을 되돌려 잰 크기에 여유를 둔 것이다. 넘으면 블록을 줄이거나 지난 기록을 옮긴다('종료와 작업 공간 정리'). 새 기록 파일은 처음부터 이 값 안에서 시작한다. 두 번 연속 넘거나 도구의 읽기 한도가 바뀌면 값을 다시 정한다.

목록 유지가 두 번 연속 작업당 약 5분을 넘으면 중복 칸·갱신 횟수를 줄인다. 수치는 초기 경보값이며 효과의 입증이 아니다. 실제 인계·동시 작업이 없으면 효과는 미검증이다. 병합 대기가 반복적으로 본 작업을 막았다는 기록이 있을 때만 위임을 재검토한다. 첫 관찰 기간에는 새 병합 봇·상시 감시기·맥락 주입 훅을 추가하지 않는다.

## 커밋 기록

- 커밋에는 과거에 왜 바꿨는지를 쓴다. 현재 상태와 다음 행동은 작업별 인계에 쓴다(위 '시작과 공유 진행 목록'). squash 병합이면 작업 브랜치의 커밋 메시지가 보호 브랜치에 남지 않으므로 커밋 이력이 작업 경과 기록을 대신하지 않는다. 남길 경과는 인계 이력과 PR 본문에 둔다.
- 형식은 `.gitmessage`를 따른다. 제목은 `<type>: <요약>`이다. 필수 칸과 경고 칸은 `gitops.config.json`의 `commit.requiredFields`·`commit.warnFields`가 기준이다. 검증 칸은 훅이 검사하지 않지만 쓴다(검증하지 않았으면 미실행이라고 쓴다).
- 요청·Issue·작업 ID로 인용한다. 문서 위치는 절 번호 대신 절 제목으로 쓰고, 과거 위치를 특정해야 하면 커밋 해시를 붙인다.
- 트레일러(`Refs:`, `Co-Authored-By:` 등)는 맨 끝에 빈 줄 없이 둔다.
- 이유를 찾을 때: `git log --follow -- <file>`, `git log -L :<func>:<file>`, `git log --format='%h %(trailers:key=Refs,valueonly)'`.
- `commit-msg`는 제목 형식, 필수 칸, 메시지 안의 비밀 값만 검사한다. staged diff의 비밀 값·개인정보는 커밋하는 쪽이 직접 점검한다.

## 장치와 한계

- 서버 쪽 브랜치 보호(공개 저장소 또는 유료 플랜)를 쓸 수 있으면 보호 브랜치에 "PR 필수"와 "gitops guards 검사 필수"를 켠다. 쓸 수 없으면 CI 실패는 병합을 막지 못하고, 모든 장치는 로컬 실수 방지용이다. 권한 경계가 아니다.
  <!-- TODO(gitops): 이 저장소에서 서버 보호를 쓸 수 있는지와 확인한 날짜를 적고 이 줄을 지운다. -->
- 설치(clone마다 한 번): `node scripts/gitops/setup.mjs`. 훅 폴더와 커밋 양식을 이 저장소 설정에만 연결한다. 점검만: `node scripts/gitops/setup.mjs --check`. worktree는 설정을 공유한다. 다른 훅 설정(전역 `core.hooksPath`, husky 등)이 있으면 setup은 바꾸지 않고 안내한다. 그때는 그 훅에서 `node scripts/gitops/commit-msg.mjs "$1"`과 `node scripts/gitops/pre-push.mjs "$@"`를 부른다.
- 검증: `node --test "tests/gitops/*.check.mjs"` (Node 22+, Git 필요). 인자 없는 `node --test`는 프로젝트의 다른 테스트까지 실행하므로 쓰지 않는다.
- 장치:
  - `.githooks/commit-msg` → `scripts/gitops/commit-msg.mjs`: 커밋 메시지 형식과 메시지 안의 비밀 값 검사.
  - `.githooks/pre-push` → `scripts/gitops/pre-push.mjs`: 어느 원격이든 보호 브랜치의 생성·갱신·삭제 push를 거부한다. 사람도 해당된다. 보호 브랜치 반영은 GitHub의 PR 병합으로만 한다.
  - `scripts/gitops/guard-tools.mjs` + 에이전트 도구 설정(`.claude/settings.json`, `.codex/hooks.json` 등): 에이전트가 셸 명령이나 MCP 병합 도구를 실행하기 전에 검사해 PR 병합, 보호 브랜치 push, 훅 우회(`--no-verify`, `commit -n`, hooksPath 변경)를 막는다.
  - `.github/workflows/gitops.yml`: 위 장치가 바뀌는 PR에서만 검사를 돌린다.
- 한계:
  - guard는 명령 문자열만 본다. 스크립트·Makefile·셸 별칭 안의 명령과 이름에 merge가 없는 MCP 도구는 보지 못한다. 보호 브랜치 push는 pre-push가 한 번 더 막지만 PR 병합은 다시 막는 장치가 없다.
  - 훅은 체크아웃된 파일에 달려 있다. 이 장치를 들이기 전 브랜치를 체크아웃한 worktree에는 훅이 없다.
  - commit-msg는 메시지만 본다. diff 안의 비밀, GitHub 화면에서 만든 커밋(squash 메시지 포함), 숫자가 없는 비밀은 놓친다.
  - 에이전트 도구마다 보호 수준이 다르다. Codex는 프로젝트 훅을 신뢰해야 실행된다. 실제로 막히는지 도구마다 한 번 확인한다.
  - GUI Git 클라이언트에서 node를 찾지 못하면 커밋과 push가 막힌다.
  - 설정 파일이 없거나 깨지면 훅과 guard가 모두 막는다. 파일 편집으로 고친다.

## 넣지 않은 장치와 다시 필요해지는 조건

검토했지만 넣지 않은 장치다. 조건이 실제로 관찰되면 ADR로 결정하고 더한다.

| 장치 | 다시 검토할 조건 |
|---|---|
| 에이전트 병합 위임(경로로 등급을 판정해 중·저위험만 에이전트가 병합) | 저위험 PR 판정이 실제로 승인자에게 부담이 될 때. 경로 판정 우회(따옴표 처리된 경로, 실행 위치·설정에 따른 판정 변화)를 먼저 해결한다 |
| PR 사실 검사(Issue 필수·검증 SHA·CI 이름) | 서버 보호를 쓸 수 있고, 필수 항목이 빠진 PR이 반복될 때 |
| 맥락 주입(커밋 이유·ADR을 세션에 자동 주입) | 낡은 이유로 결정이 뒤집히는 사고가 실제로 관찰되고, 측정 담당자가 정해졌을 때 |
| 프로젝트 인증 실행기 | 프로젝트별로 다른 GitHub 계정·토큰이 필요해질 때 |
| 인계 초안 스크립트 | 인계 누락이 반복될 때 |
| 현재 상태 크기·목록 불일치 검사 | `상태 불일치`나 읽기 경보값 초과가 두 번 이상 기록될 때 |
| 중단 때 자동 기록 훅(세션 종료·맥락 압축 전) | 중단 뒤 복원 실패가 두 번 이상 기록될 때. 도구에 따라 사용자 중단에는 종료 훅이 실행되지 않으므로 실제로 실행되는지 먼저 확인한다 |
| ADR 대체 링크 양쪽 검사 | 대체한 ADR과 대체된 ADR 중 한쪽만 링크가 바뀐 일이 관찰될 때 |
| Issue 양식 | Issue로 요구를 관리하기 시작할 때 |
| diff 비밀 검사(gitleaks 등) | staged diff의 비밀 값이 실제로 커밋된 일이 생길 때 |
